### Faults the owner confirmed on the render (2026-10-24)

1. **MONSTER ENERGY wordmark missing next to the claw on both doors.** The design has only the claw on `left_mid` and `right_mid`; the wordmark is on the roof only. The review said "0 layers missing" because the claw image is named `monster_claw` and matches the wordmark layer's word "monster": **the coverage check matches by words, so one brand's two marks vouch for each other.**
2. **On the wing it typed MONSTER as text** instead of using the logo file, against the rule "never redraw a brand mark". Nothing checks a text element against a fetch layer's brand.
3. **The grey art is much darker than the references** (turn 2: dark cracks), then in turn 3 **faint thin light lines** (colour #a7a7a3, opacity 0.85): never the soft light-grey feathers. The model's turn 3 message still calls it "feathers/vines", although the user had asked "tell me if you can't". **No pattern generator in the kit can make feather plumes** (`ink-lines`, `leaves`, `cracks`, `splatter`, `brush`); the model cannot fix this by tuning, and neither could Haiku.
4. The zip without a name or picture (fixed in turn 3 once the user asked).

## Findings for the kit (ordered; none built yet)

1. **The art gap is the biggest.** Options: (a) a `plumes` pattern generator (soft tapered feather shapes, light grey, low opacity, density by panel); (b) ask the user for the original art (B18) and give the agent a place to put it (`assets/art/`) with a layer type "art file"; (c) a hard rule in the review: when a tonal-art layer is generated, print "this is line art, the reference shows soft plumes: tell the user it is not the same" so the report cannot call it feathers.
2. **Coverage by asset, not by words.** For a `fetch` layer with an `asset`, count only elements that use that file; so a claw on the doors cannot vouch for the wordmark layer, and the missing wordmark shows as `missing:`.
3. **Brand text check.** A text element that spells a `fetch` layer's brand (MONSTER, PORSCHE, MOTUL...) gets a warning: use the logo file, or record a decision.
4. **Ship step visible.** After the build with nothing missing, `apply`'s review prints "ready to ship: `apply --export` builds the zip with the name and picture, then `validate skin`, then `brief set <slug> report`". The low-level `export` help says "prefer `apply --export`", and `export` warns when `ui_skin.json` is missing. Models stop running `brief show` after the first turns, so the hint has to be in `apply`'s own output.
5. **A check-in before the heavy work.** After the sourcing plan, before building, the agent tells the user in a few lines what it found, what has no file, what it will leave out or fake, and asks (plan check-in). Today the first question came after 38 minutes and the placeholder was already in.
6. **Test the ask path**: re-run with the aerial photo removed and with a photo set where a logo is ambiguous.
7. Smaller: `docs/TODO.md`-style files linked from the README do not exist for a user; the README should not send an agent to files it cannot open (and the worked example in `examples/` will tempt a model to copy it).
